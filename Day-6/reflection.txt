Reflection Document - Day 6 AI Internship

1. How does an AI application communicate with an LLM?
Before I built this, I used to think LLMs were somehow running inside the Python code itself, but now I get that it’s just a standard web API call. Here's how it actually works under the hood:
- The application uses the `google-genai` Python library (or direct HTTP libraries like `requests`) to build a structured JSON payload containing my prompt, model selection, and configs (like temperature, top-k, etc.).
- The SDK sends this payload as an HTTPS POST request over the internet to Google's backend API servers (specifically `https://generativelanguage.googleapis.com/`).
- Google's servers receive it, pass the prompt to their massive GPU/TPU accelerator hardware to run the model weights, and predict the output.
- Once the AI finishes generating, Google packages the output text and some metadata into a JSON response, sends it back over HTTP, and my Python script parses it to print the text in the terminal. It's basically a typical client-server loop, just with a giant neural network in the middle.

2. What role does the API key play?
The API key acts as a combined digital ID card, secret password, and billing meter.
- Why we need it: It proves to Google's servers who is making the request, verifies that my account is allowed to use that specific model, and tracks how many input and output tokens I'm using so they can bill me (or limit my free tier usage).
- Security warning: Since the key is tied directly to my billing account, anyone who gets a hold of it can run up huge charges or lock my account. This is why hardcoding keys in `chatbot.py` or uploading them to public GitHub repositories is a huge mistake. I made sure to load it from a local `.env` file instead and added `.env` to `.gitignore` to keep it safe.

3. What happens when a user sends a prompt?
Here’s the step-by-step lifecycle of a message in the terminal chatbot I built:
1. Taking Input: The console waits for my input, I type a question (like "Explain Python"), and hit Enter.
2. Assembling the History: Since LLMs are stateless (they don't remember previous messages), the Python SDK fetches the entire history of our conversation so far and appends the new prompt to it. This is how the chatbot "remembers" context.
3. Sending the Request: The SDK serializes this whole history list into a structured JSON payload, attaches the `GEMINI_API_KEY` to the headers for authorization, and makes the HTTPS POST request to Google's API server.
4. Generation: Google's servers run the input tokens through the model, predict the reply token-by-token, and return the complete response.
5. Display & Logging: The python script receives the response, prints the text to the terminal, appends the readable chat to `chat_history.txt`, and saves a structured JSON log of the conversation turns in `chat_log.json`.

4. What did you learn while building the chatbot?
This was a super cool exercise, and I learned a bunch of useful engineering concepts:
- Using the GenAI SDK: I got hands-on experience with the new unified `google-genai` library. The `client.chats.create()` helper is awesome because it manages the conversation history state automatically under the hood so I don't have to manually append messages to a list.
- Dealing with API Errors: I realized external APIs aren't always 100% reliable. Sometimes you get 503 (service busy) errors. To handle this, I set up a fallback chain that tries `gemini-1.5-flash` first, and if that fails, automatically tries `gemini-2.5-flash` or `gemini-1.5-pro`.
- Aesthetic Terminal Design: I structured the terminal layouts and logs to give the chatbot a clean and readable terminal output instead of just unstructured text.
- Environment Safety: Using `dotenv` to load the `GEMINI_API_KEY` from a local file, and setting up an `.env.template` so anyone else cloning my project knows exactly what environment variables they need.

5. What improvements would you add?
If I had more time to work on this, here's what I'd build next:
- A Proper Web UI: The terminal is cool, but a simple web interface using Streamlit or Next.js would look much cleaner and be easier for normal people to use.
- Streaming Responses: Right now, the chatbot pauses and then dumps the entire answer at once. I want to implement token streaming so the text types out in real-time as it's generated.
- SQLite Database: Instead of dumping chats into plain text files, saving them to a local SQLite database would let me organize conversations by sessions or search past chats easily.
- Persona Settings: Letting users choose a system instruction prompt (like "Explain as a pirate" or "Review my code as a senior dev") before starting the chat.
- Token Usage Meter: Displaying the exact input/output token count and estimated cost for each query so users know how much resource they are consuming.
